# Plan: temple-bar 0.2.0

Theme: **agent rules and the merge loop, frozen for grand-union.** Our
AGENTS.md uses the template's block, the plan moves to ADRs, the template gains
the rules agents keep missing, merge and ready stop wasting runs or deleting
the wrong thing, and the gate checks that every file is type-checked and
tested. grand-union adopts temple-bar, in place, once 0.2.0 ships.

Scope frozen by the maintainer on 2026-10-24: nothing joins unless something
leaves. The plan was approved the same day. Baseline main `2242813`, judged by
published 0.1.0. Tracker:
[#397](https://github.com/londontypescript/temple-bar/issues/397).

This builds on an unapproved draft of 2026-10-19. Where today's decisions
differ (#391 and #258 above all), today's stand.

## Decisions

Settled on 2026-10-24 in one decide-first pass, each reviewed adversarially by
ChatGPT Sol 6.1 before it came to the maintainer. The full record of each is a
comment on its issue. They are numbered 80 to 89 and recorded, with what each
rejected, in [ADR 0016](../adr/0016-agent-rules-and-the-merge-loop.md).
Decision 28's new wording is in
[ADR 0002](../adr/0002-what-temple-bar-is-for.md).

- **Decision 28, reworded:** grand-union adopts temple-bar, in place, once
  0.2.0 ships. The remaining themes continue alongside, ordered by incidents
  from grand-union and tate-modern. Its start moves again only if scope leaves
  at the same time. This answers
  [#94](https://github.com/londontypescript/temple-bar/issues/94) for
  grand-union.
- **80. Merge keeps the merged branch's worktree** and its local branch, and
  reports them. Removing them is left to whatever made the worktree and to
  `temple-bar leftovers`. No refusal to run outside the primary checkout.
  - [#391](https://github.com/londontypescript/temple-bar/issues/391)
- **81. One GitHub reference per line.** In a pull request description, each
  reference sits on its own nested line under its change bullet, on one
  physical line, or on a standalone line when there are no bullets. Merge is
  unchanged: it already keeps only top-level bullets.
  - [#383](https://github.com/londontypescript/temple-bar/issues/383)
- **82. `ready` fetches the default branch alone before the gate, refuses a
  branch that is behind it, and stops if the fetch fails.** Only `ready`
  fetches; `pre-push` makes no network call.
  - [#262](https://github.com/londontypescript/temple-bar/issues/262)
- **83. The gate requires the AGENTS.md block** in every repo set up with
  temple-bar: a missing file or block fails, with "run setup again". The pin
  bump to 0.2.0 regenerates this repo's block.
  - [#258](https://github.com/londontypescript/temple-bar/issues/258)
- **84. Agents create worktrees only through their harness,** never with
  `git worktree add` or a location of their own; a harness limit is raised
  with the user once per session.
  - [#392](https://github.com/londontypescript/temple-bar/issues/392)
- **85. An oversized pull request needs a `One concern:` line,** like one
  closing several issues. Source and test lines are counted apart: 500 source
  lines, 1,000 test lines, 15 files combined, by default. A failed measurement
  refuses. The size report reuses merge's own check of the line.
  - [#393](https://github.com/londontypescript/temple-bar/issues/393)
  - [#382](https://github.com/londontypescript/temple-bar/issues/382)
- **86. A pull request the judge will refuse** carries exactly the squash
  body as its description, and the maintainer's checklist in a separate
  comment.
  - [#270](https://github.com/londontypescript/temple-bar/issues/270)
- **87. A pin bump's mixing is disclosed, not yet refused:** the judge's
  refusal lists every other changed path, and the checklist asks for the
  manifest and lockfile diffs.
  - [#234](https://github.com/londontypescript/temple-bar/issues/234)
  - the hard refusal is deferred to
    [#426](https://github.com/londontypescript/temple-bar/issues/426)
- **88. The gate checks that every tracked file is type-checked and tested,**
  bound to the scripts the gate actually runs, with exclusions only in
  `temple-bar.config.json`.
  - [#394](https://github.com/londontypescript/temple-bar/issues/394)
- **89. Every decision lives in an ADR;** the decisions list becomes an index
  in `docs/adr/`.
  - [#259](https://github.com/londontypescript/temple-bar/issues/259)

Agent decides, within stated bounds:

- [#303](https://github.com/londontypescript/temple-bar/issues/303): probe
  real GitHub first, then order a check's runs by workflow run and attempt,
  with the check-run ID only as a tie-breaker.

## Waves

No two phases running at the same time touch the same file. Merges go one at a
time from the primary checkout with `pnpm merge <N>`, and each later branch
merges `main` in first.

1. **P0 first,** alone: it records the decisions every brief cites.
2. **Then at once:** P1, P3, P4, P5 (once its brief passes review), P7, P8's
   probe and design, P9 and W.
3. **As phases land:** P2 after P1; P6 after P5; P8's build after its brief
   passes review, its config field after P7.
4. **Release:** once everything has merged. Prepare 0.2.0; the tag and publish
   need the maintainer's yes; then the pin bump on its own, regenerating our
   block.

Critical paths: P0 → P1 → P2 on the docs side, P5 → P6 on the merge side, and
P8 on its own.

## Who does what

Approved by the maintainer on 2026-10-24, with the efforts for this run: every
Opus builder at high effort, extra-high for delicate work, since the run has
capacity to spare.

- **Orchestrator:** one session that runs this plan, on Fable 5.1 for this
  run. It writes P0 itself, writes every brief, reviews every line, owns the
  shared files, keeps the decision log, and does every push and merge.
- **Subagents** for the contained phases, each in its own harness-made
  worktree. They commit only; the orchestrator pushes and merges.
  - Opus 5.5 at high effort: P3, P4, P6, P7, P9 and W.
  - Opus 5.5 at extra-high effort: P5 (delicate).
- **Child sessions** for the phases that are long or go back and forth with the
  maintainer, so the orchestrator's context stays clean and the maintainer can
  open and steer them. They commit only too, and report back to the
  orchestrator, which pushes and merges.
  - **Docs session (P1, then P2),** Opus 5.5 at high effort. It drafts our
    AGENTS.md, the ADR move and the template text, and agrees each with the
    maintainer before its push.
  - **Coverage session (P8),** on Fable 5.1. It runs the probe, designs the
    brief, because a wrong first design is costly to undo, and has the build
    done by an Opus 5.5 subagent at extra-high effort.
- **ChatGPT Sol 6.1:** adversarially reviews the briefs of P5 and P8, then
  re-checks each revised brief (effort medium). It reviews every code pull
  request alongside the orchestrator (effort high).

## How the run decides

The plan is approved up front so the run can go on its own:

- **Decide and log:** anything that follows from a decision above or a
  principle already written down, such as how to fix a bug the plan didn't
  foresee.
- **Stop and ask:**
  - anything touching scope, AGENTS.md, the README, publishing or the checks;
  - anything that changes a decision above;
  - any recommendation that adds cost or friction the maintainer would feel:
    more CI time, manual steps, more approvals.
- **Never by confidence.** How sure the agent is doesn't move a decision from
  one list to the other.
- **The orchestrator writes its own view before reading a builder's
  recommendation,** then compares the two.
- **Every decision taken without the maintainer** goes in a log on #397, one
  line and a reason each, for the maintainer to skim.

## Verification

- Every new check has remove-the-fix evidence: the check fails with its own
  message, then the fix is restored.
- The full suite always runs.
- Delivery is verified by installing what `pnpm pack:local` packs.
- A failed Windows leg is reproduced on the Windows machine with the targeted
  run first (W), the full run only when the failure isn't localised.
- The release tier runs before 0.2.0 is staged.

## After 0.2.0

grand-union's own decide-first pass and first milestone can be drafted while
0.2.0 builds. Its first work after adoption is clean-up: remove its own gate
script, CI and template-feedback files, let setup add its block to its
AGENTS.md, and move PLAN.md's open items into issues. Then a review of the
spike against its architecture. A secrets scan of its history comes before it
goes public.
