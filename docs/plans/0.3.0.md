# Plan: temple-bar 0.3.0

Theme: **new repositories from zero.** The milestone's issues are placed by the
maintainer:
[milestone 0.3.0](https://github.com/londontypescript/temple-bar/milestone/8).

**This plan is partial on purpose.** The maintainer asked for the Windows CI
speed-up first, so the plan holds
[#454](https://github.com/londontypescript/temple-bar/issues/454)'s phases
and the parallel Windows gate that came out of it,
[#463](https://github.com/londontypescript/temple-bar/issues/463), and
nothing else. The rest of the milestone is planned later, after its
decide-first pass, in a pull request that extends this file. Nothing below
claims a file another 0.3.0 issue names.

## Decisions

#454's own plan was approved by the maintainer on 2026-10-25, after an
adversarial review by ChatGPT Sol 6.1 and Claude Fable 5.1 and a re-check by
ChatGPT Sol 6.1. Its record, measurements included, is on the issue.

- **Phase W1 caches git's index only within an explicit batch of writes,**
  not once per run (safe today only through call order) and not by watching
  the index file's stat (inode and timestamp edge cases, and a timestamp guard
  would remove the gain).
- **W1 records a new ADR,** taking the next number: it changes the "nothing
  cached" design of the fix that made setup never write through a symlink.
  - [#300](https://github.com/londontypescript/temple-bar/issues/300)
- **W2 uses neither `fast-import` nor a long-lived `cat-file --batch`:** the
  first breaks the tests that delete a loose object, and the second needs an
  asynchronous fake for a small gain.

- **W1 was dropped** on 2026-10-26: its forecast saving (about 30 to 75 s
  per Windows job) wasn't worth weakening the check on staged symlinks, so its
  ADR was never accepted. W2 merged. The reasons and numbers are on #454.
- **#463's six decisions,** approved on 2026-10-27 after an adversarial
  review by ChatGPT Sol 6.1, are on the issue: parts are the gate's own split
  (repo, root, each package); the repo-wide checks are their own part; a
  verifier over successful part jobs proves completeness; Windows legs only;
  not in the template yet; and a frozen benchmark comes before any code.

Notes:

- **G0, G1 and G2 run in order.** G0 needs no pull request. G1 lands, then

  profiling run on #454; it gets a phase only if the numbers justify one.
- **The ADR's number** is taken when G1 is written.

## Who does what

- **Orchestrator:** this session, on the primary checkout. It writes every
  brief, reviews every line, owns the shared files, and does every push and
  merge.
- **Builders:** one per phase, each in its own harness-made worktree,
  committing only. Proposed, for the maintainer to confirm before each
  starts: Opus 5.5 at extra-high effort for G1 (delicate), Opus 5.5 at high
  effort for G2 (involved). G0 is the orchestrator's.
- **ChatGPT Sol 6.1:** adversarially reviews G1's brief before it builds,
  then re-checks the revised brief (effort medium). It reviews every code
  pull request alongside the orchestrator (effort high).

## Verification

- Every new check has remove-the-fix evidence.
- The full suite always runs.
- Performance claims come only from a frozen benchmark with its threshold set
  first, never from ordinary CI times.
