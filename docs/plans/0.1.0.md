# Plan: temple-bar 0.1.0

Theme: **workspaces.** Temple Bar sets up at a pnpm workspace root, finds every
app and shared package, runs each package's checks, and stops a pull request
from weakening those checks.

Scope and order approved by the maintainer on 2026-10-11. Baseline main
`f7ff858`, judged by published 0.0.10. Tracker:
[#366](https://github.com/londontypescript/temple-bar/issues/366).

## Evidence

Two trials came first. Neither changed production code.

- The minimal workspace trial,
  [#309](https://github.com/londontypescript/temple-bar/issues/309#issuecomment-6103677235),
  found:
  - Unchecked packages and missing or weakened child scripts get past both gate
    and judge.
  - Child pins are caught only through the lockfile.
  - Any edit to the workspace YAML is guarded as a whole.
- The [stack trial](https://github.com/londontypescript/temple-bar-stack-trial-314/tree/75da4fa44c68bf2d4750b6097cfaa091edc03738)
  built grand-union's layout: React/Vite web, Fiber/Three scene, Ink CLI,
  Electron, and shared TypeScript source. It installs, checks, builds and runs
  with strict peers. Its phase results are on #366. It also found:
  - The normal launcher fails at a workspace root with `ERR_PNPM_ADDING_TO_ROOT`.
  - A custom root Vitest config and a noncanonical Electron entry need precise
    Knip configuration.
  - Knip's own entry-export check and the stronger check disagree.
  - The lockfile parser refuses an ordinary-width catalog lockfile.

## Contracts to settle before code

One decision packet, reviewed adversarially before it comes to the maintainer.
Each answer is recorded in the plan's decisions list before the code that
depends on it starts.

- **Release numbering
  ([#354](https://github.com/londontypescript/temple-bar/issues/354)):**
  settled on 2026-10-11. A planned release raises the minor version and a fix
  the patch (decision 2), so this milestone, first named 0.0.11, is 0.1.0.
  grand-union starts after the release candidate, 0.5.0 (decision 28).
- **Checked packages
  ([#311](https://github.com/londontypescript/temple-bar/issues/311),
  [#312](https://github.com/londontypescript/temple-bar/issues/312)):**
  settled on 2026-10-11 after an adversarial Codex review, as decisions 63
  to 67 in [ADR 0015](../adr/0015-every-package-checked-and-guarded.md).
  The judge guards every script of every tracked `package.json`, so
  [#285](https://github.com/londontypescript/temple-bar/issues/285) joins
  phase 6. A new or removed package needs the maintainer, and
  `pnpm-workspace.yaml` stays guarded as a whole file.
- **Entry points
  ([#313](https://github.com/londontypescript/temple-bar/issues/313)):**
  - How Knip finds each target's real entries, and recognises shared exports
    that only sibling packages use.
  - Current entry-export rules stay. Stricter rules need a later decision.
  - No broad entry globs or ignores.
  - Settled on 2026-10-15 as decision 74: temple-bar generates no Knip
    configuration. Knip runs once at the root over the whole graph, and the
    gate attributes its findings to the root or a package by path. Entries
    Knip's plugins don't find are declared in the project's own Knip config.
- **The rest of 0.1.0** (decisions 68 to 74, approved on 2026-10-15 after
  ChatGPT Sol 6.1's adversarial review):
  - Phase 5 settled that the gate re-runs only the pnpm that started it,
    named by `npm_execpath`, never one from PATH; setup writes a root `ready`
    script so `pnpm ready` hands that path over (decision 68, on
    [#311](https://github.com/londontypescript/temple-bar/issues/311)).
  - `temple-bar merge` runs the gate in-process too, so setup writes a root
    `merge` script and the docs say `pnpm merge <N>`, run from the
    default-branch checkout: it runs whatever the current folder's manifest
    says, so never inside a pull request's worktree. The core check and the
    judge make a changed `merge` script a failure; they don't protect the
    invocation itself (decision 69,
    [#401](https://github.com/londontypescript/temple-bar/issues/401)).
  - The gate re-runs its starter in three launcher forms, resolved once for
    the listing and every script: a JavaScript entry through `process.execPath`;
    a native executable on disk, run directly with no shell; anything else
    (a `.cmd` shim, a path that doesn't exist) fails the inventory and marks
    the root's scripts not run, with install advice. Whether the standalone
    pnpm is supported is the maintainer's call after a probe of `@pnpm/exe`
    (decision 70,
    [#402](https://github.com/londontypescript/temple-bar/issues/402)).
  - Phase 6 builds to ADR 0015 as written: `pnpm-workspace.yaml` stays
    guarded whole, and #285 closes with decision 64; the pull request carries
    a `One concern:` line (decision 71).
  - Phase 6 is one builder; its packed judge tests are written by a second
    subagent in a worktree of its own, after the orchestrator extends the
    fake GitHub API to serve manifest contents, statuses and inconsistent
    file lists, and integrated by the orchestrator (decision 72).
  - Phases 6 and 7 build at the same time in separate worktrees and land in
    order; phase 8 follows (decision 73).
- **A release tier of tests** (decision 75, approved on 2026-10-17 after
  ChatGPT Sol 6.1's adversarial review): tests whose cost comes from
  installing real third-party frameworks form a release tier,
  `pnpm test:release`, in `e2e/release/`, named so plain `node --test` never
  runs them. Every pull request runs only `pnpm test`, where every promise
  keeps at least one test on the minimal workspace; the release tier only
  confirms those promises on a real stack. It runs by hand during a
  milestone (the release-check workflow, dispatched on any branch), and the
  release workflow requires it, on the six OS and Node pairs, before it
  stages a version on npm. Its direct dependencies are pinned and their own
  dependencies resolve fresh, so it is also a compatibility check against
  today's npm. The gate still typechecks, lints, formats and runs knip over
  its files on every pull request. Which test goes in which tier is a review
  rule, not a mechanism: the coverage map in each pull request that adds
  release-tier tests is what the reviewer checks. The maintainer found real
  installs on every pull request unsustainable.

Phase 4a lands before phase 5 because phases 5 to 8 add many packed tests that
create temporary repositories. Phases 4b and 4c land before phase 5 too: 4b
makes the runtime test run on Windows, and 4c needs it for phase 3's rerun.
Phase 4d shares no files with the others and lands first, so trials on existing
projects stop meeting a refusal whose advice leads back to it.
From phase 5 on, CI's Windows legs judge every pull request. The Windows
machine is for when one of them fails: `pnpm windows-run` is where the
failure is reproduced and looked at, and it runs again on the fix before
that fix is pushed
([#370](https://github.com/londontypescript/temple-bar/issues/370)). That
second push is an ordinary CI correction, which decision 35 (push once,
when finished) allows: it rules out pushing drafts, not fixing a failed
check. A failure that does not reproduce on the machine is diagnosed and
the diagnosis recorded before any workaround, as for any other failure. A
phase whose design depends on Windows behaviour may also run it while the
work is in progress. Running it before every push, as agreed on
2026-10-12, was dropped on 2026-10-15 after
[#398](https://github.com/londontypescript/temple-bar/pull/398): a run
takes about twenty minutes on a machine a tenth of the Mac's speed, while a
Windows leg in CI runs alongside the others and finishes in six to eleven,
so even a failure found in CI costs less time than a run before every
push. What is given up: a failure that only the machine's environment shows
(Node under Program Files, a standard user account, Defender) is no longer
caught before a merge; the machine keeps that value for debugging and for
Windows-dependent design. Since 0.2.0 a failed Windows leg is reproduced
with the targeted run first (`pnpm windows-run --only <file>`, seconds once
installed), and with the full run only when the failure isn't localised to
one file; the fix is then confirmed the same way
([#404](https://github.com/londontypescript/temple-bar/issues/404)).

Phases 2 and 3 are separate pull requests because setup and runtime change
different behaviour. Phases 2 to 5 ran in sequence: phases 5 to 8 share one
inventory, and phases 2 to 8 share packed-test helpers.

After phase 5 (merged 2026-10-15 as cf3dbd4), the remaining work runs in
waves (decisions 69 to 74):

1. At the same time: 5a and #260, each its own pull request; the `@pnpm/exe`
   probe and the maintainer's policy, then 5b; and the orchestrator's
   preparation for phases 6 and 7: a comment on #312 citing decision 66, the
   fake GitHub API extended, the phase 6 brief drafted and reviewed
   adversarially by ChatGPT Sol 6.1 (with a re-check of the revised brief),
   the phase 7 brief drafted with its fixture files named. 5a lands before
   phase 6's build starts.
2. Phases 6 and 7 build at the same time, in separate worktrees, once their
   briefs are approved. Their delegated files are disjoint; shared work
   (this plan, `docs/enforcement.md`, `e2e/support/`, root manifests) is the
   orchestrator's, once per phase at integration. Phase 6 lands first; phase
   7 lands after it through `temple-bar merge`, which merges `main` into the
   branch and reruns the gate. A pull request that changes a workflow,
   AGENTS.md or the checks' own config (#260) is the maintainer's admin
   merge instead.
3. Decision 75 recorded, and #414 built, at the same time; both land before
   phase 8 starts. #414 was found while planning phase 8: the stack trial's

   #417 lands before phase 8 too: #414's Windows run hit Git for Windows'

4. Phase 8. It changes workflows, so the maintainer admin-merges it. The orchestrator then dispatches the release check on

## Who does what

- **Orchestrator:** Claude Code (Opus). It drafts the decision packet, writes
  phases 1 and 4, reviews every line, and owns shared files.
- **Implementation:** one subagent per phase. Phases 2 to 5 ran one at a
  time (Opus for phase 5, Sonnet for 2 and 3). From phase 5a on, the
  maintainer's standing choice (2026-10-15) is Claude Opus at medium effort
  for every subagent, and Opus at high effort for delicate work: phase 6's
  builder, with its packed tests by a second Opus-medium subagent (decision
  72). From phase 8 on (2026-10-17), work rated involved runs Opus at high
  effort too, and routine work Opus at medium: phase 8's builder ran at
  high. The orchestrator passes the model and effort explicitly on every
  launch.
- **ChatGPT Sol 6.1 (through the Codex CLI):** adversarially reviews the
  decision packet and each delicate brief, then reviews each code pull
  request alongside the orchestrator.

## Verification

- Every new check has remove-the-fix evidence: the check fails with its own
  message, then the fix is restored.
- The full suite always runs.
- Delivery is verified by installing what `pnpm pack:local` packs.
- GUI and PTY delivery are exercised on macOS only. Windows and Linux prove
  gate and build in CI; the Windows machine is where a failed Windows leg
  is reproduced.
- Not in scope:
  - Electron packaging.
  - SSH hosting.
  - Release-candidate acceptance ([#196](https://github.com/londontypescript/temple-bar/issues/196), 0.5.0).
